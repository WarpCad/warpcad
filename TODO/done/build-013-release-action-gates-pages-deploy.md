## Goal

Stop deploying GitHub Pages on every merge to `main`. Replace that trigger with a deliberate
**Release** action: a manually started GitHub Actions workflow that, for one chosen commit on
`main`:

1. bumps the version in `package.json`,
2. writes a changelog entry and a GitHub release whose notes describe what changed since the
   previous tag,
3. creates and pushes the `vX.Y.Z` tag,
4. builds and deploys the Pages site from that tagged commit.

`main` keeps running CI on every push and pull request, as today. Only the Pages build and
deploy move to the release path. Done means: a merge to `main` produces no Pages deployment; a
release run produces one tag, one GitHub release with generated notes, and one Pages deployment
of exactly that tagged commit.

The user has used `release-it` before and found it works well. This file adopts it as the
default, subject to the Library decisions process in `CLAUDE.md`. The implementing task must
compare it against the alternatives before pulling it in (see Testing).

## Interaction model

n/a: no user-visible app control. This is CI and release tooling only. The end-user-facing
surface is the GitHub release page, which is reviewed by the maintainer, not the app's users.

## Documentation

n/a: no change to the app's user-visible controls. The maintainer-facing procedure (how to cut
a release, what the Pages workflow now needs) goes in `CONTRIBUTING.md` and the release-procedure
section of `PUBLISH-CHECKLIST.md`, which are maintainer docs, not the `docs/` site.

## Problem

`.github/workflows/pages.yml` runs `workflow_run` on every completed `CI` run for `main`, so
each merge redeploys Pages. The user does not want that: a release should be a deliberate act,
with a version, a tag, and notes. Today there is no tag and no release (`git tag` is empty),
`package.json` is still `0.0.0`, and nothing records what changed between deployments.

There is a constraint that shapes the design. A release created or tagged with the default
`GITHUB_TOKEN` does **not** trigger other workflows on `release` or `push: tags` events (GitHub's
guard against recursive workflow runs). A `release: published` trigger in `pages.yml` would
silently never fire. `workflow_dispatch` is the exception: it is allowed to trigger from
`GITHUB_TOKEN`. The design below uses that rather than a personal access token.

## Affected files

- `.github/workflows/release.yml`              (new: `workflow_dispatch` with a bump input; runs release-it, then calls the Pages workflow)
- `.github/workflows/pages.yml`                (drop `workflow_run`; accept a `workflow_call` and `workflow_dispatch` with a `ref` input; keep the build and deploy steps as they are)
- `package.json`                               (add `release-it` and `@release-it/conventional-changelog` as devDependencies; add a `release` script)
- `.release-it.json`                           (new: `git.requireBranch: main`, `git.requireCleanWorkingTree`, `github.release: true`, `github.releaseNotes` from the changelog, `npm.publish: false`, conventional-changelog preset)
- `CHANGELOG.md`                               (new, generated by release-it on each release)
- `docs/decisions/release.md`                  (new: the library comparison, per `CLAUDE.md`'s Library decisions section)
- `scripts/release-workflow.spec.js`           (new: guard, see Testing)
- `CONTRIBUTING.md`, `PUBLISH-CHECKLIST.md`    (maintainer procedure: how to cut a release; the one-time setup)
- `TODO/VERIFY.md`                             (one row: the first real release is a one-off check)

## Proposed fix

**Library choice.** Write `docs/decisions/release.md` before adding any dependency. It compares
at least `release-it` (with `@release-it/conventional-changelog`), `semantic-release`, `changesets`,
and a hand-rolled script that calls `npm version` and `gh release create`, on: features, size,
stars, open/closed issue ratio, release recency, and maintainer count. It has a rejection table
for each runner-up. Recommend `release-it` unless the comparison finds a concrete problem with it.
The user's prior experience counts as evidence to weigh, not as the decision itself. Check the
licence against the allow-list. `release-it` is MIT, version 21.1.1, at the time of writing.

**Commit convention.** Recent commits use Conventional Commits (`feat(ai): …`, `ci(deps): …`), so
the changelog preset can derive entries from history. Confirm this holds across the range a first
release will cover. If it doesn't, the changelog comes out thin, and that's a finding to file, not
something to hide.

**Release workflow (`release.yml`).**
- Trigger: `workflow_dispatch` with a `bump` input (`patch` | `minor` | `major`) and an optional
  `ref` (defaults to the head of `main`).
- Gate first: refuse unless the target commit's `CI` run concluded `success`. The release must not
  tag a commit that failed its own tests.
- Permissions: `contents: write` for the tag, the release, and the changelog commit. Nothing else.
- Run `release-it --ci --increment <bump>`. It bumps `package.json`, updates `CHANGELOG.md`,
  commits, tags `vX.Y.Z`, pushes, and creates the GitHub release with the changelog section as its
  notes. `--ci` makes it non-interactive.
- Then call the Pages workflow with `uses: ./.github/workflows/pages.yml` and `with: ref: <the tag>`.
  This is a `workflow_call` into a reusable workflow, which is the reliable way to chain them under
  `GITHUB_TOKEN`.

**Pages workflow (`pages.yml`).**
- Remove the `workflow_run` trigger, so merges no longer deploy.
- Add `workflow_call` (with the `ref` input) and keep `workflow_dispatch` (also with a `ref` input,
  so a Pages rebuild of an old tag is possible).
- `actions/checkout` uses `ref: ${{ inputs.ref || github.sha }}`. The Pages build then runs on the
  tagged commit, not on whatever `main` is at.
- Keep the existing source-map upload, LFS cache, and `concurrency: pages` group unchanged.

**Sentry release key.** Sentry groups errors and source maps by a `release` string. The app sends
`VITE_SENTRY_RELEASE` with every error, and the workflow uploads source maps under `SENTRY_RELEASE`.
Sentry only unminifies a stack trace when those two strings match exactly. Today both are the commit
SHA (`github.event.workflow_run.head_sha || github.sha`). Keep the SHA; changing the key to a tag name
is a separate decision and not part of this task.

The SHA must be the commit that is actually built. The release commit is created by `release-it` (the
version bump and changelog), so the tag points at a commit that is not the one the release run was
dispatched from. `github.sha` in the called workflow would be that older commit, and every error would
then fail to match its source maps. So `SENTRY_RELEASE` and `VITE_SENTRY_RELEASE` are read from the
checked-out commit (`git rev-parse HEAD`), not from `github.sha`. Record in the release notes which tag
points at which SHA, so an error can be traced to a version.

**Version and tag scheme.** The first release is `1.0.0`, taken from the current `0.0.0` in
`package.json` via a `major` bump on the first run, or set explicitly. Tags are `vX.Y.Z`.

**One-time setup, for the maintainer.** Repository settings: keep Pages source as "GitHub
Actions." No new secrets are needed under this design, since `GITHUB_TOKEN` suffices. If branch
protection on `main` ever blocks the release commit from being pushed, the fix is to allow the
`github-actions` bot to push, not a PAT. Note that in `PUBLISH-CHECKLIST.md`.

## Testing

- **Unit guard, Vitest.** `scripts/release-workflow.spec.js` parses both workflow files as YAML
  and asserts: `pages.yml` has no `workflow_run` trigger and no `push`/`pull_request` trigger; it
  accepts `workflow_call` and `workflow_dispatch`; `release.yml` is `workflow_dispatch` only; its
  job has `contents: write` and nothing broader; it calls `pages.yml`; and it runs `release-it`
  with `--ci`. This mirrors the guard style of `scripts/sentry-build.spec.js`.
- **Config guard.** The same spec checks that `.release-it.json` sets `npm.publish: false` and
  `git.requireBranch: main`, so a misconfigured release cannot publish to npm or tag a feature
  branch.
- **Local dry run.** `npx release-it --dry-run --ci --increment patch` on a clean checkout of
  `main` prints the planned version bump, changelog section, tag, and release notes without writing
  anything. Record its output in the implementing PR description.
- **Lint.** `actionlint` (or the repo's equivalent, if one exists) passes on both workflows.
- **Not testable here, and recorded as a one-off in `TODO/VERIFY.md`:** an actual release run
  against GitHub. It tags, pushes, and deploys Pages, and it must be run by the user. Until it has
  run once, the `workflow_call` chaining is unverified.
- **E2E.** None. There is no UI change, so no `*.e2e.js` spec is added, and no browser engines or
  viewports apply.
- **Acceptance scenarios it could break.** None. This changes the deploy trigger, not the app. The
  deployed app is the same build, from a tag instead of a merge.
- **Closed findings it extends.** `build-009` (source-map upload keyed on the commit SHA) and
  `build-012` (LFS cache in the Pages build). Re-run each one's original check after this change:
  the Pages build still restores the GIFs from the cache, and the Sentry upload still names the
  release by SHA and still fails on HTTP error.
