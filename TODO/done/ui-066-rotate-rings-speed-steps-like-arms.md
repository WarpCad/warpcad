## What actually shipped (retirement note, 2026-10-15)

As proposed. `rotateStepDeg(shift, speedStepDeg)` drops its pointer-type parameter: Shift wins,
otherwise the speed step (a cold start is the finest band, never continuous). `usesSpeedStep` is gone;
`isFingerPointer(pointerType)` stays for the readout's finger-dodging placement only. The ring's speed
tracker and stall timer in `Viewport.vue` run for every pointer type. The mouse e2e now asserts a step is
in force (band-tolerant) and the touch speed-band test runs for both `touch` and `mouse`. Band edges were
**not** tuned: a 60-move crawl with plus or minus 0.8 px of hand jitter at a 67 px ring radius read within
plus or minus 0.7 degrees at `fine 0.1°`, which is what the old continuous mouse read too, so there is no
evidence a pointer-type branch or new edges are needed.

## Goal

`ui-065` open question (a), agreed with the user on 2026-10-15 after the translate ruler was
checked on an iPad. Today the two gizmo kinds differ:

| Pointer | Translate arrow (`ui-065`) | Rotate ring (`ui-064`) |
|---|---|---|
| Mouse, no Shift | speed picks the step | **continuous** |
| Mouse, Shift | 1 mm | 5° |
| Touch / pen, no Shift | speed picks the step | speed picks the step |
| Touch / pen, Shift | 1 mm | 5° |

"Done" is: a plain **mouse** ring drag picks its step from drag speed, exactly as a touch drag
does, so the table's two columns match in every row. Shift still wins over speed, and release
still commits exactly the displayed angle as one `transform.rotate`.

The behaviour change is deliberate and is the same one `ui-065` made for arms: a slow mouse drag
lands on sub-degree values without a modifier, and a fast one moves in 5-15° steps.

## Interaction model

- **Precondition / trigger / selection**: unchanged. Exactly one body selected; press and drag a
  rotate ring.
- **Feedback**: unchanged dial and readout (`ui-064`). The step line under the readout now also
  appears on mouse drags (`5° steps`, `fine 0.1°`), because a step is now in force.
- **Small-screen behavior**: unchanged; touch already behaved this way.

## Documentation

- **Page**: `docs/selection-and-inspector.md`, *The rotation dial*. Remove the "mouse is
  continuous" wording and say the speed rule is the same for a mouse, a pen and a finger, and the
  same as for arrows. Update the example's step 5 so it is not "on a tablet" only.
- **Media**: `gizmo-rotate-dial.gif`/`.png` are regenerated by `npm run docs:media` only if the
  recorded drag now steps (it should, slightly); look at them before committing.

## Affected files

- `src/render/rotateSnap.js`: `usesSpeedStep(pointerType)` and `rotateStepDeg(shift, pointerType,
  speedStep)` stop depending on the pointer type (`translateStepMm` in `translateSnap.js` is the
  model: Shift wins, otherwise the speed step).
- `src/components/viewport/Viewport.vue`: the ring branch's speed tracker and stall timer run for
  every pointer type, not touch/pen only (the arm branch already does).
- `src/render/rotateSnap.spec.js`, `src/render/annotate.spec.js` (`placeDialReadout`'s `touch`
  flag keeps meaning "dodge a finger", which is still a pointer-type question, so leave it).
- `e2e/rotate-dial.e2e.js`: the mouse test that asserts a *continuous* readout must change; add a
  mouse slow-down variant mirroring `translate-ruler.e2e.js`.
- `docs/selection-and-inspector.md`.

## Proposed fix

1. Make `rotateStepDeg` ignore `pointerType`, with its tests rewritten first (RED): a mouse drag
   with a slow speed reads `0.1°`, a fast one coarse, Shift wins.
2. Run the ring's speed tracker for all pointer types in `Viewport.vue`; keep the readout's
   finger-dodging placement keyed on `pointerType`.
3. Update the mouse e2e from "continuous" to the new behaviour. This is the test most likely to be
   timing-sensitive; assert on the band, as `ui-064` and `ui-065` do.
4. Docs, then the usual verification.

## Open questions

- **Mouse jitter.** A mouse sampled at a human pace is noisier than a finger. If a plain mouse
  ring drag feels twitchy at the lowest band, the fix is band edges (one constant table), not a
  pointer-type branch. Judge this by hand before tuning.
- **Opt-out.** If anyone wants continuous mouse rotation back, hold-Shift is the wrong key (it
  snaps). Not proposed; flag it if it turns out to matter.

## Effort

S. The code change is small and the translate path is the template. The cost is in re-checking
the mouse feel by hand.

## Testing

- **Unit**: as in Proposed fix (1), explicit tolerances, plus a test that a touch drag's results
  are unchanged.
- **E2E**: `e2e/rotate-dial.e2e.js` at all three viewports and all three engines, because the
  ring drag is the engine-sensitive surface `CLAUDE.md`'s Browser Support section names.
- **Acceptance scenarios to re-drive by hand**: **1** (rotate one of two bodies; both remain),
  **10** (a snapped `+45.0°` and a fine `+12.3°` reload exactly), **12** if reachable.
- **Closed findings whose repro gets re-run**: `ui-064` (every row of its Testing section,
  especially Shift and the speed bands on touch), `ui-012`, `core-004` (rotation composed, not
  summed).
- **Hand drive with a real mouse**, since the mouse feel is the whole change.
