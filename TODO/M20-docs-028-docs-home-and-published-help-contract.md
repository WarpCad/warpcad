## Goal

M19 (the Tauri apps) and M20 (the `warpcad.com` home page) both link to the documentation in
`docs/`. The owner asked (2026-10-26) whether the docs belong here or in one of those
repositories, and how they are built and maintained for all three.

**Answer: the source stays in `warpcad/docs/`.** None of the three consumers reads the Markdown.
They all read what `scripts/vite-plugin-help.mjs` publishes:

| Consumer | What it reads | When |
|---|---|---|
| The web app's Help sheet | `help/index.json`, `help/<slug>.html`, `help/img/…`, same origin, precached | every build of this repository |
| The home page (`docs-027`) | `https://app.warpcad.com/help/index.json` and `app-overview.png` | its daily rebuild |
| The native apps (M19) | the same `help/` folder inside `dist-native/`, bundled by `build:native` | each native build |

Moving the source to another repository breaks three things this one relies on. Every docs
picture is generated by driving this repository's UI (`e2e/docs/*.docs.js`, `npm run docs:media`,
guarded by `e2e/docs-media.spec.js`), so the pages and the specs that make their pictures must
change together. CLAUDE.md's per-task Documentation gate puts a control and its docs page in the
same task and commit. And the in-app Help is built from `docs/` by this repository's Vite build.

The missing piece is the other half: **the published Help is a public interface, and nothing
treats it as one.** The home page will link 31 `#/help/<slug>` URLs, the App Store listing will
link `#/help/privacy` (`build-020`), and people will bookmark and share help views
(`docs/help.md`, "Sharing a help view"). Renaming `docs/booleans.md` today breaks all of those
without a warning. `help/index.json` does not say which build produced it, so a native app pinned
to an older commit cannot tell that web-hosted Help describes a newer app. And the M19 rows
disagreed on the native docs page's name (fixed when this row was filed; step 6).

Done means:

1. `docs/decisions/documentation.md` records where docs live, how they are built, the published
   contract, and how each consumer reads it, with the rejection table below.
2. `help/index.json` says which build produced it.
3. A slug that was ever published keeps working: removing or renaming a page without an alias
   fails the build, and an alias opens the new page.
4. CLAUDE.md, `docs/README.md` and the M19/M20 TODOs say the same thing as the record.

### Rejection table (for the decision record)

| Option | Why not |
|---|---|
| Move `docs/` into `warpcad.github.io` (M20) | The app would depend on its own marketing site. Every UI task would need a commit in two repositories, and the docs-media specs would run in a different repository from the pages they illustrate |
| Move `docs/` into `warpcad-native` (M19) | Same problems, and the native-only pages are a handful of the 31. The native apps run this repository's UI, so their pages describe this repository's code |
| A separate `warpcad-docs` repository, consumed as a submodule or npm package | Three repositories in step instead of one. A version pin to bump on every UI change, and the media generator still needs the app, so it would stay here anyway |
| A second rendering on `warpcad.com/docs/` | Already rejected in `docs-026` question 4: two renderings to keep in step, and a second copy of about 70 MB of GIFs |
| **Keep the source here; publish `help/` as a versioned contract** (chosen) | One source, one renderer, one media pipeline. Consumers depend on a published URL and a schema, not on a file layout |

**Revisit when** search traffic matters (`docs-026` question 4's trigger). The cheap path is in
this repository: have the help build also emit a crawlable page per slug
(`app.warpcad.com/help/<slug>/`, the same fragment in a minimal shell with an **Open in WarpCad**
link and a canonical URL). That keeps one renderer. A second site does not.

### Who writes which docs

- **End-user docs**, for every platform, go in `warpcad/docs/` only. That includes native-only
  pages and sections. A TODO filed in `warpcad-native` that changes what a user sees edits
  `../warpcad/docs/` and carries a `> Two repositories` banner. Its docs change passes this
  repository's gates (`npm run spdx`, the help build's link check, `e2e/docs-media.spec.js`).
- **Developer docs** live next to the code they describe: `warpcad-native/README.md` (how to
  build the shell), `warpcad.github.io/README.md` (how the home page builds), and this
  repository's `CONTRIBUTING.md` and `docs/decisions/`.
- **The home page's own copy** (hero, What it does) is page copy in `warpcad.github.io`, not docs.
  It links to docs pages and never restates them.

### How the native apps include Help

This task does not choose. That choice is `build-020`'s, step 1: ship the GIFs or not, and the
prose licence's (a) or (b) in `docs/decisions/app-store-licensing.md`. It records the three shapes
the contract supports, so whichever answer the owner gives is a configuration change in
`build:native`, not a redesign:

| Shape | Bundle size | Offline | Licence fit | Cost |
|---|---|---|---|---|
| **Bundled** (today's `dist-native/`) | +89 MB of GIFs | Full | Needs (a) | None. It is what `build:native` does now |
| **Bundled text and stills, GIFs from the web** | +about 19 MB | Text and stills | Needs (a) | `helpRuntimeCaching()`'s GIF pattern points at `app.warpcad.com`, and the shell's CSP allows that one `img-src` |
| **All Help from the web** | +0 | None until visited | Fits (b) | `helpUrl()` gains a build-time base (`VITE_HELP_BASE`), and the shell's CSP allows `connect-src`/`img-src` for `app.warpcad.com`. Must show **version skew** (see item 2 below) |

GitHub Pages serves `help/` with `Access-Control-Allow-Origin: *`. `docs-026` records that for
the index. Confirm it for `help/<slug>.html` and `help/img/` with `curl -I`, and write the result
in the record.

## Interaction model

Most of this task is a decision record and a build guard. It changes one user-visible behaviour:
an old help link opens the page that replaced it.

- **Precondition**: none. A cold first visit, as in `testing-012`.
- **Trigger**: opening `https://app.warpcad.com/#/help/<old-slug>`, where `<old-slug>` is an alias
  in `docs/help-slugs.json` (a link on another site, a bookmark, a shared help view).
- **Feedback**: the Help sheet opens on the **new** page, titled as in Contents. The hash is
  rewritten to `#/help/<new-slug>` with `history.replaceState`, so a copy of the address from
  then on is the current one, and Back does not return to the old slug. A slug that is neither a
  page, a topic id nor an alias gets `testing-012`'s pinned unknown-slug outcome.
- **Placement / Selection response / Selection count**: n/a.
- **Small-screen behavior**: unchanged. The same sheet at the same widths as `testing-012`.

## Documentation

- **Page**: `docs/help.md`, "Sharing a help view", gets one sentence: "A link to a help page keeps
  working if the page is later renamed: WarpCad opens the page that replaced it." `docs/README.md`
  gets a short contributor note below its picture paragraph: renaming or removing a page means
  adding an alias in `docs/help-slugs.json`. The build says so if you forget.
- **Example** (for `docs/help.md`): "Open `https://app.warpcad.com/#/help/<an alias>`. The Help
  sheet opens on **<the new page's title>**, and the address bar now ends in
  `#/help/<new-slug>`." If no real rename exists when this lands, the e2e uses a fixture alias
  and the page states the rule without a live example.
- **Media**: none. The behaviour is an address change, and a still shows nothing the existing
  `help-*` shots do not.

## Affected files

- `docs/decisions/documentation.md` (new): the Goal's answer, the consumer table, the rejection
  table, who writes which docs, the three native shapes, the CORS check, **Revisit when**.
- `docs/help-slugs.json` (new): `{ "slugs": [...], "aliases": { "<old>": "<new>" } }`, listing
  every page slug and `TOPICS` id published so far (the live index's 31 slugs plus
  `src/help/topics.js`'s ids). JSON has no SPDX rule in `scripts/spdx.mjs`, so it carries no
  marker, like `package.json`.
- `scripts/help-build.mjs`:
  - `helpIndex()` adds `schema: 1`, `version` and `commit`: the same `APP_VERSION` and
    `APP_COMMIT` that `vite.config.js` puts in `<meta name="version">`, passed through
    `warpcadHelp({ version, commit })`. It also adds `aliases` from the lockfile. Existing
    fields keep their shape, so the app and `docs-027` need no change to keep working.
  - A lockfile check: every listed slug must be a page, a topic id or an alias. An alias must
    point at a page or topic, never at another alias. A page or topic missing from the list fails
    with a message naming it and the fix (`npm run help:slugs`).
- `scripts/help-slugs.mjs` (new) and a `help:slugs` script in `package.json`: appends new slugs
  to the lockfile. It never removes one; a removal is an alias, added by hand.
- `scripts/vite-plugin-help.mjs`: pass the version and commit through, in dev too (`dev`).
- `src/help/loader.js`: `IndexPage`/`HelpIndex` typedefs gain the new fields, plus a
  `resolveSlug(index, slug)` that follows an alias.
- `src/components/layout/HelpSheet.vue`: `openFromHash()` resolves through `resolveSlug` and
  calls `replaceState` when it followed an alias.
- `CLAUDE.md`: Project Structure's `docs/` line becomes "end-user documentation, rendered into
  the in-app Help by `scripts/help-build.mjs`, and published at `app.warpcad.com/help/` for the
  home page and the native apps. See `docs/decisions/documentation.md`." That replaces "tool TBD".
- `docs/README.md`: the "docs-site tool is still TBD" paragraph is replaced with the same fact.
- `docs/decisions/home-page.md` (if `docs-026` has written it) or `TODO/M20-docs-026-…` question 4
  and 5: link the new record. The index's `version`/`commit` go into `docs-027`'s
  `help-index.snapshot.json` as they are.
- `TODO/M20-docs-027-…`: `scripts/check.mjs` ignores `aliases` when it checks that every link is
  in the index. Links are built from `pages`, never from aliases.
