**Machine**: Apple M4 Pro, 14 cores, 24 GB, macOS 27.0, Node v24.14.1.
**Browser**: Playwright 1.63.0, Chromium 153.0.8010.12, **headless, software rasteriser**.
**Build**: browser rows run the **production build** (`npm run build && npx vite preview

**Fixtures**: generated from action records in the scripts themselves, no binary files.
`fillet-50` is `data-004`'s 200-record fixture (50 cubes, each moved, rim-filleted and

**Runs**: browser n=5 per cell, a fresh context per run (autosave would otherwise restore
the previous run's scene); Node n=11 per cell. Medians reported with the spread.

## 1. Where the main thread's kernel time actually went (Node, before)

`core-029` offered two shapes to choose between with measurements: one RPC the whole
document fold goes through, or an "expensive ops only" boundary with a measured threshold.
The first thing measured was therefore *where the time goes*, split three ways per
interaction: **fold** (the mutation itself — `evaluate()` plus the command layer),
**summary** (`stores/document.js`'s `refresh()` summarising every body, which ran
`boundsOf` + `volumeOf`, each a full `combine()` — a kernel union — per composite), and
**transport** (what shipping every body across a worker boundary would cost).

| scene | interaction | fold | **summary** | transport |
|---|---|---|---|---|
| fillet-50 | drag-place (append one cuboid) | 0.0 | 1.4 | 4.9 |
| fillet-50 | boolean (union the last two bodies) | 0.4 | 0.6 | 5.0 |
| fillet-50 | Inspector-style move | 0.0 | 0.9 | 4.8 |
| fillet-50 | **Undo** (full re-fold) | **77.8** | 0.8 | 4.8 |
| fillet-50 | edit the **first** row (full re-fold — `data-004`'s 67 ms) | **69.8** | 0.8 | 4.8 |
| 24-bodies | drag-place (append one cuboid) | 0.0 | **113.3** | 9.7 |
| 24-bodies | boolean | 4.2 | **96.6** | 9.0 |
| 24-bodies | Inspector-style move | 0.0 | **126.1** | 9.2 |
| 24-bodies | **Undo** | **163.1** | **143.7** | 9.2 |
| 24-bodies | edit the first row | **157.1** | **117.2** | 10.2 |

And option 2's threshold — each op evaluated alone, median (p95), ms:

| op | median | p95 |
|---|---|---|
| `primitive.cuboid` / `cylinder` | 0.0 | 0.0 |
| `primitive.sphere` | 0.1 | 0.3 |
| `transform.translate` | 0.0 | 0.0 |
| `boolean.union` (2 cuboids) | 0.0 | 0.1 |
| `boolean.subtract` (cuboid − sphere) | 3.5 | 5.0 |
| `modify.filletRim` | 1.4 | 2.1 |
| `hardware.bolt` recipe | 0.3 | 0.4 |
| `raspberrypi.bplus` recipe | 0.7 | 14.0 |

**What this says.** No single op is expensive: the worst median is 3.5 ms. An
"expensive ops only" boundary would have had nothing to move — the cost is *aggregate*,
in two places neither candidate shape named:

1. **The summary**, 97-144 ms per mutation on the composite scene — including a drag-place
   of one Cube, because every *unchanged* body was re-unioned on every refresh. This was
   the largest block, and it was not evaluation at all but *measurement*. The same
   `boundsOf` → `combine()` also ran over every body at the start of every placement drag
   (`refreshSnapNeighbours`), on every marquee, and on selection (Inspector).
2. **The full re-fold** on Undo/Redo and every timeline row action: 70-78 ms (fillet-50)
   and 157-163 ms (24-bodies), linear, kernel-dominated.

Transport is cheap either way: 5-10 ms to pack, clone and unpack every body.

A side measurement settled half of item 1 without any worker at all: the box of a union
is the box of its parts' boxes. Measured on all 13 library composites that build with
default params, part-by-part bounds equal the union's to within **7e-15 mm**, at
**~0.01 ms** instead of 1-8 ms per composite.

## 2. What changed, and the Node breakdown after

- `boundsOf` measures a hole-free group part by part — no union (exact, see above).
- A composite's **volume** (it genuinely needs the union) is measured in the new evaluation
  worker, cached per geometry object, `null` in the summary until it lands.

"Summary" below is now the store's real `summarizeBody`, main-thread share only, with a
**cold cache** every run (a fresh fold — the worst case, what an Undo pays). "Worker" is
what the evaluation worker spends on the composites the summary left pending.

| scene | interaction | fold before / after | **summary before / after** | worker (off thread) |
|---|---|---|---|---|
| fillet-50 | drag-place | 0.0 / 0.0 | 1.4 / 1.0 | 0.0 |
| fillet-50 | Undo | 77.8 / 72.4 | 0.8 / 0.7 | 0.0 |
| fillet-50 | edit the first row | 69.8 / 71.6 | 0.8 / 0.6 | 0.0 |
| 24-bodies | drag-place | 0.0 / 0.0 | **113.3 / 0.1** | 49.8 |
| 24-bodies | boolean | 4.2 / 4.1 | **96.6 / 0.1** | 50.5 |
| 24-bodies | Inspector-style move | 0.0 / 0.0 | **126.1 / 0.1** | 54.7 |
| 24-bodies | Undo | 163.1 / 154.6 | **143.7 / 0.1** | 53.1 |
| 24-bodies | edit the first row | 157.1 / 132.9 | **117.2 / 0.1** | 68.1 |

In the app the worker column is smaller still: the cache means only a body that actually
changed is sent, so a drag-place of a Cube sends nothing and a drag-place of a Pi sends one
Pi. It is this large here only because every run starts cold.

The **fold** column did not move and was not meant to: that is the second half of the
decision, filed as `TODO/core-030` with these numbers.

**Reading it honestly.**

- On the composite scene every interaction but Undo went from hundreds of milliseconds at
  phone-class throttling to about a frame or two. Undo lost its summary half and kept its
  re-fold half.
- `fillet-50` has no composites, so this change has nothing to move there: its numbers
  are unchanged, as they should be. **`data-004`'s headline — the 200-record re-fold on
  Undo, 89/282/426 ms — is not moved by this task.** It is the fold, and it is
  `TODO/core-030`.
- The drag-place floor of ~70-90 ms on **both** scenes barely responds to CPU throttling
  (fillet-50: 77 → 80 → 92 ms across 1×→6×), so it is not main-thread CPU. The likely
  owner is the headless software rasteriser uploading a new mesh; a CPU profile of that
  window is the next thing to take, and this headless setup cannot say what a real GPU
  does (`perf-benchmark.md` rule 5).
- Boolean and Inspector on the composite scene now sit at 19-28 ms at 1×-4×: over the
  16 ms budget, but by the same margin as the composite-free scene, i.e. no longer
  kernel-bound.

## 4. The worker is real in both engines, in the production build

Placing a `raspberrypi.bplus` against `vite preview`: Chromium and WebKit both spawn
`assets/evaluation.worker-*.js` (161.5 kB, and in the service-worker precache: 9 entries,
up from 8), both land the same volume, **22579.354 mm³**, and neither logs a console
error. `e2e/evaluation-worker.e2e.js` proves the same against the dev server at all three
viewports in both engines, comparing the worker's number to the main thread's
`measureGeometry` of the same geometry in the page, digit for digit. Firefox cannot launch
in this sandbox (`TROUBLESHOOTING.md`, 2026-09-17).
