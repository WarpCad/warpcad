# `TODO/perf-005`: the bundle-load bench against the deployed build

**Machine**: Apple M4 Pro, 14 cores, 24 GB, macOS 27.2.1, Node v24.22.2. **Browser**: Chromium
153.0.8010.12 (headless, software rendering), laptop viewport 1440×900, 7 recorded runs and 1
unrecorded warm-up per cell, every run a fresh context. Run 2026-11-15 05:09-05:18 UTC, from a home
connection, one run at a time.

**Commands**

- Deployed: `node bench/bundle-load.mjs --url https://app.warpcad.com/ --runs 7`
- Local, same method: `vite preview --outDir dist --port 4300` and
  `node bench/bundle-load.mjs --url http://127.0.0.1:4300/ --runs 7`
- Local, original method (in-server pacing, regression check for local mode):
  `node bench/bundle-load.mjs --engines chromium --runs 7 --build local=dist`

**What differs from local mode.** `--url` has no server to pace or meter, so Chromium does both:
`Network.emulateNetworkConditions` (150 ms added to each request's real round trip, 200 kB/s down) and the
same 4x CPU rate for `slow4g-cpu4`; request counts and bytes come from Playwright's request events
(`request.sizes()` for the encoded body, the response body's length for raw JavaScript). A response
the service worker answered is dropped, as the local server never sees it. Chromium only. The
localhost `--url` run reproduces local mode's byte counts exactly (JS wire 681.4 against 680.9 kB,
JS raw 2,279.6 kB in both), which is the check that the browser-side counting is right.

**The two builds differ.** The deploy is `index-C5t6lvOB.js`, last modified 10 Nov. The local `dist/` is
`index-BIRuvguV.js`, built 14 Nov from the working tree (no DSN, no measurement ID). Everything in the
deploy's boot list that the local build lacks is traced to one file, below.

## What the extra deployed file is

`esm-C4pqlg3y.js` is the Sentry SDK 11.8.0: 429 kB raw, 144.0 kB gzip (`curl -H 'Accept-Encoding: gzip'`).
`.github/workflows/pages.yml` gives the deploy build `VITE_SENTRY_DSN`, so Sentry initialises during
boot and its chunk is on the cold path. The local build has no DSN, so the chunk is emitted and
never fetched. `perf-002`, `perf-003` and every local bench run measured the no-DSN shape.
Without that chunk the deploy's boot JS is 803.3 - 144.0 = 659.3 kB gzip, and the AI agent, the tool registry and the dev provider are absent from the boot list, so the `perf-003` deferral is still
in effect on the deploy.

## Against the `perf-002` #1 questions

- **Does the fragmented builds' request cost shrink on HTTP/2?** The deploy makes 6 page requests
  to usable and the local build 5, so there is no request-count change to see here (this repo
  ships the one defer-boot layout; the fragmented variants were out-of-tree candidates and are not
  deployed). Unthrottled, the real transport costs about 70 ms on the cold path (344 against 273 ms),
  and the deploy also carries 122 kB more JS, so that gap is an upper bound on the TLS and CDN cost.
- **Does the ~330 ms defer-boot gain hold?** Not measurable as a delta: one build is deployed. What
  can be shown is that the deferral is present and the gain's mechanism (about 66 kB less boot JS at
  200 kB/s) is intact; the deploy's boot JS is 659 kB without Sentry. The Sentry chunk is 144 kB
  that a DSN-less bench never saw, and at 200 kB/s it is a 720 ms cost on a real mobile link if it is
  on the critical path. Filed as `perf-006`.
- **Unexplained, flagged:** at `slow4g` the deploy's cold load (4,069 ms) is 138 ms faster than
  the local build's through the same method (4,207 ms) while moving 115 kB more. A strict 200 kB/s
  budget predicts about 575 ms slower. CDP throttling evidently charges a real HTTP/2 transfer
  differently from a plain HTTP/1.1 localhost one. So the deployed `slow4g` and `slow4g-cpu4`
  absolutes are for comparing deployed runs with each other, not with the local tables, to within
  a few hundred ms. The unthrottled and repeat cells do not have this problem.

## Local mode still reproduces (closed-finding regression)

`perf-002` and `perf-003`'s local numbers, re-run in local mode on today's tree: slow4g cold 4,260
(`perf-003` `new`: 3,759; `main` has grown since, and the working tree carries uncommitted theme
work), none cold 238 (254 / 238), repeat-sw 190 / 191 (190 / 189), 5 requests (5). Repeat cells and the
unthrottled cold cell are within 15 ms of `perf-003`; the slow4g cold gap is the build's growth in
JS (680.9 kB against 605.1 kB, +76 kB at 200 kB/s is +380 ms, 3,759 + 380 ≈ 4,140 against 4,260 measured).
Local mode's code path is untouched except that `tally` prefers a hit's own `raw` size when present
(only deployed mode sets it).
