# `TODO/perf-006`: the Sentry chunk with a DSN set, before and after deferring it to the first frame

**Machine**: Apple M4 Pro, macOS 27.2.1, Node v24. **Browser**: Chromium (headless, software
rendering), 1440x900, 5 recorded runs and 1 warm-up per cell, fresh context each run.

**Builds**: both built with the dummy DSN `VITE_SENTRY_DSN=https://k@o.invalid/1` (no events can be
sent): `before-dsn` is HEAD `88eb8d14`, `after-dsn` is the working tree with the fix.

**Command**: `node bench/bundle-load.mjs --build before-dsn=<dir> --build after-dsn=<dir> --engines chromium --profiles none,slow4g --runs 5`
(no bench change was needed: it already takes several `--build` directories).

| profile | build | cold usable ms | cold JS wire kB | cold JS requests counted |
|---|---|---|---|---|
| slow4g | before-dsn | 4324 (4292-4326) | 838.4 | 6 |
| slow4g | after-dsn | 4324 (4308-4327) | 694.0 | 6 |
| none | before-dsn | 257 (255-258) | 838.4 | 6 |
| none | after-dsn | 255 (254-271) | 838.6 | 6 |

**Reading it.** Under the 200 kB/s link the Sentry chunk (`esm-*.js`, 144 kB gzip) is no longer
transferred before usable: JS wire falls 838.4 to 694.0 kB. `usable` did not move (4324 ms both): at
that link the first frame is bound by the main chunks, and the old early request was still in flight
at usable, so the win is bytes taken off the cold path and off the link the app's own chunks share,
not a measured time drop here. On localhost (`none`) the fetch starts at the first frame and lands
before the bench's second-frame mark, so bytes match. No errors in any run.

**Not run**: `--url https://app.warpcad.com/`, because the fix is not deployed. After the deploy,
run `node bench/bundle-load.mjs --url https://app.warpcad.com/ --runs 7` and confirm `esm-*.js` is not
in the cold JS list.
