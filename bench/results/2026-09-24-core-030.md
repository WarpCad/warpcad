## 3. How much real use option 2 covers

Every Undo/Redo press in a scripted session is classified by whether the kernel ran **at
all**. That is counted at the registry boundary, as op lookups through a `Proxy` over the
real registry, and not inferred from timing.

| session | before: restored / re-folded | after: restored / re-folded |
|---|---|---|
| scenario 12's steps (edit, suppress, roll back, insert, move, with their Undo/Redo) | 0 / 3 | **3 / 0** |
| build 10 steps, Undo ×10, Redo ×5, Undo ×5 | 2 / 18 | **20 / 0** |
| an MCP write lands between two local steps, then Undo ×2, Redo ×2 | 0 / 4 | **3 / 1** |

The "before" count of 2 in the second session is an artifact: re-folding an empty or
one-record log performs no lookups.

In the third session the one re-fold is the Undo that has to reach **behind** the MCP
write. That is correct: the state captured before the local step does not contain the MCP
record, so restoring it would delete someone else's work. The Redo after that fold is a
restore again, because a fold-path Undo still captures the state it replaced.

**Reading it.** In a single-user session every Undo and Redo within the last 50 steps
(`restorableSteps`) is served by restore. Only a non-local write in between, or a step
older than 50, re-folds. The row actions themselves still re-fold synchronously, and so do
Open and autosave restore. That is the remaining option-1 work, filed as `TODO/core-031`
with these numbers.
