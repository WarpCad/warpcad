# `TODO/perf-001` — export off the main thread: before and after

**Machine**: Apple M4 Pro, 14 cores, 24 GB, macOS 27.0 (Darwin 25.x), Node v24.14.1.
**Browser**: Playwright 1.63.0 Chromium, headless, software rasteriser — every number
below is CPU-bound serialization with no GPU work, which is why headless is acceptable
here and would not be for a rendering benchmark.
**Build**: Node rows run the source directly; browser rows run the **dev server**
(`npm run dev`, port 5183), because the benchmark seeds documents through
`/src/stores/…`. The production build was separately verified to emit, load and run the
worker chunk in Chromium *and* WebKit (`dist/assets/export.worker-*.js`, 172 kB) with a
real `cube-1.stl` download and no console errors.
**Fixtures**: `bench/fixtures/export-scenes.js` and `bench/export-mainthread.mjs`'s own
`SCENES` — generated from action records, no binary fixtures.
**Warm-up**: 5 discarded runs per cell in Node; a fresh browser context per run in the
browser (`io-001` restores the last document from IndexedDB, so reusing a context would
inherit the previous run's scene).

Two changes are measured here, and they are reported separately because they are
separable:

1. **`makeWatertight` made near-linear** — integer corner identity instead of string
   keys, plus a uniform spatial hash over welded corners walked along each open edge.
2. **Export moved into a worker** — `src/core/export.worker.js`, entered only from the
   export path.

## 1. The work, in Node (`node bench/export-benchmark.mjs --runs 20`)

`watertight` is `makeWatertight` alone, summed over the scene's bodies. `stl` / `obj` /
`glb` are the whole export, repair included. All times in **milliseconds**.

### `makeWatertight` alone — the change this task was filed for

| scene | polygons in | n | before (min / **median** / p95) | after (min / **median** / p95) | median speed-up |
|---|---|---|---|---|---|
| one `raspberrypi.bplus` | 217 | 20 | 1.51 / **1.71** / 1.93 | 0.30 / **0.39** / 0.69 | **4.4×** |
| 24 bodies (12 Pi + 12 bolts) | 3,492 | 20 | 26.04 / **27.01** / 27.95 | 3.83 / **4.82** / 6.78 | **5.6×** |
| one large solid (sphere `segments: 96` ∪ cube) | 4,107 | 20 | 19.01 / **20.18** / 21.39 | 3.21 / **3.79** / 6.11 | **5.3×** |
| one huge solid (sphere `segments: 192` ∪ cube) | 16,275 | 5 | 88.03 / **89.92** / 93.82 | 14.74 / **20.78** / 23.63 | **4.3×** |

Scaling, which is the point: before, 3.96× the polygons cost 4.45× the time; after,
3.96× the polygons cost 5.5× the time on the p50 but from a five-times-lower base — the
remaining growth is the per-pass edge tally, not the corner scan. The old quadratic term
(open edges × every corner in the solid) reached 2.38 M candidate tests per pass on the
huge solid; the spatial hash removes it.

### Where the 24-body export's time actually goes — the finding's own assumption, corrected

| phase | before | after |
|---|---|---|
| `toGeom3` (combining 24 Group bodies — real kernel booleans) | 43.4 | 43.4 |
| `makeWatertight` | 28.0 | 4.8 |
| `stlSerializer.serialize` | 8.7 | 8.7 |

`TODO/perf-001` was written as though the repair were the dominant cost. On the
multi-body scene it is not: **the `combine()` of composite bodies is**, at 43 of the
57 ms that remain. That single measurement is what settled the architecture question
below — optimising the repair alone could never have got this scene under budget,
because 76% of its cost is in a part the optimisation does not touch.

### What a worker boundary costs (the number that decides whether it is worth it)

| | 24-body scene |
|---|---|
| `packGeometry` on the main thread | **0.18 ms** |
| `structuredClone` of the packed bodies (what `postMessage` pays) | **6.5 ms** |
| the finished 618 KB STL coming back (`Uint8Array`, transferable) | **0.11 ms** |
| the work it relocates | **~57 ms** |

The clone does **not** eat the win: it costs about a ninth of what it moves.

## 2. The freeze, in a real browser (`node bench/export-mainthread.mjs`)

Worst animation-frame gap spanning the export, driven through the real controls
(**File ▾ → Export… → Export**) with the download taken. n = 5 per cell, fresh context
per run, laptop viewport 1440×900. `cpu Nx` is CDP `Emulation.setCPUThrottlingRate`;
4× and 6× bracket where a modern phone sits relative to this laptop. **A 16-17 ms
reading is the 60 Hz vsync interval — the measurement floor, i.e. no freeze at all.**

Both columns below already include the optimised repair, so this table isolates the
worker alone. Identical scene, same session.

| scene | cpu | format | no worker (**median**, min–p95) | with worker (**median**, min–p95) | improvement |
|---|---|---|---|---|---|
| 24 bodies | 1× | stl | **61.1** (57.7–62.1) | **17.2** (16.7–17.8) | 3.6× |
| | 4× | stl | **233.3** (223.7–258.4) | **27.3** (25.9–28.1) | **8.5×** |
| | 6× | stl | **346.1** (341.2–382.7) | **39.5** (36.5–41.1) | **8.8×** |
| | 1× | glb | **40.3** (39.4–45.6) | **19.8** (16.8–21.9) | 2.0× |
| | 4× | glb | **147.1** (142.1–151.9) | **27.3** (26.8–28.9) | **5.4×** |
| | 6× | glb | **222.3** (218.7–227.7) | **42.3** (39.9–44.4) | **5.3×** |

For reference, the same scene **before** the repair optimisation and before the worker
measured 58.1 / 224.1 / 339.3 ms (stl, 1× / 4× / 6×) — i.e. the repair optimisation
alone barely moved the *freeze* on this scene, exactly as the phase breakdown predicts,
because the freeze was dominated by `combine()`.

### The pending state's threshold, measured rather than asserted

`pending seen` counts runs in which `[data-testid="export-pending"]` actually appeared
in the DOM, watched by a `MutationObserver` installed before the press.

| scene | cpu | pending seen | click→download median |
|---|---|---|---|
| a Union off the origin (scenario 11's shape) | 1× | **0 / 5** | 45 ms |
| | 4× | **0 / 5** | 51 ms |
| | 6× | **0 / 5** | 69 ms |
| one `raspberrypi.bplus` | 1× | **0 / 5** | 59 ms |
| | 6× | **0 / 5** | 89 ms |
| 24 bodies | 1× | **5 / 5** | 139 ms |
| | 4× | **5 / 5** | 165 ms |
| | 6× | **5 / 5** | 196 ms |

So the 100 ms threshold does what it was asked to: a normal small export never flashes
a pending state, even at 6× CPU throttling, and a genuinely slow one always shows it.

### What is left

The residual 27-42 ms gap at 4-6× is not serialization any more — it is the 6.5 ms
clone, the Blob/download plumbing and a Vue re-render, spread over one to three frames.
It is over the 16 ms budget for one or two frames of a one-shot, user-initiated action,
which is a different thing from a third of a second of dead app. Driving it to zero
would mean transferring geometry instead of cloning it (an `ArrayBuffer` layout for
polygons), which is a kernel-wide data-structure change, not an export change.

## Reproducing

```sh
node bench/export-benchmark.mjs --runs 20
npm run dev &
node bench/export-mainthread.mjs --runs 5 --scene 24-bodies --rates 1,4,6 --formats stl,obj,glb
```

The single measurement to re-run first after any future change to this path is
**`24-bodies`, stl, cpu 4×** — it is the one that moved from 233 ms to 27 ms, and the
one a regression would show up in first.
