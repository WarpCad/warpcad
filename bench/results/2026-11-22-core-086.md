# `TODO/core-086`: the worker keeps the operands it has seen, so a repeat whole-model cut sends nothing

**Machine**: Apple M4 Pro, macOS 27.2.1, Node v24. **Browser**: Chromium, 1440x900, headless, production build.
**File**: two copies of the owner's `5036 RGB Matrix 2.5mm/5036 RGB Matrix.3mf` (1.9 MB, 25 parts, 219,540 triangles
each; never committed), placed side by side, whole-model Subtract, as `bench/results/2026-11-19-core-085.md`.

```
npm run build && npx vite preview --port 4173 &
node bench/evaluation-mainthread.mjs --only whole-model-cut --mesh "<file>" --rates 1 --runs 8
```

The spike was built and kept: the worker holds what it unpacked for a measure or boolean job under a key the page
mints per geometry object, and a cut names an operand the worker holds instead of sending it.

| Moment (n = 8 each) | Before | After |
|---|---|---|
| Click to the cut row, median (worker wait included) | 6,392 ms (5,333-6,711) | 60 ms (58-77) |
| Longest timer gap at the click, median | 21 ms (worst 23) | 17 ms (worst 168, see below) |
| Longest timer gap at the landing, median | 152 ms (worst 167) | 149 ms (worst 153) |
| Long Task at the landing, median | 120 ms | 120 ms |
| Longest gap anywhere in the window | 167 ms | 168 ms |
| Runs with a GC pause of about 1 s | 0 of 8 | 0 of 8 |
| JS heap before the click | 342-410 MB | 342-410 MB |

**Reading it.**

- **The worker's wait is gone: 6.4 s to 60 ms.** The measure job that runs when a model is placed already unpacked the
  model and built its composite union (for the volume). Before, the cut sent both models again and the worker unpacked
  them and unioned the 25 parts of each a second time; now the worker still holds the unpacked group, whose union hangs
  off the same object (`cachedCombinedOf`), so the cut is only the boolean. Here the two models are side by side, so
  that boolean is trivial; a cut that really overlaps still pays for the kernel's boolean (the e2e's cube-and-model
  case takes 4-7 s for it, as before).
- **What the click sends is nothing for a held operand.** The pack (the 4 ms slices) and the 48 MB transfer for a
  model the worker holds no longer happen; this is the pressure the one 1,022 ms GC came from. That GC did not appear
  in 8 runs before or after this session (it was 1 of 8 in the `core-085` drive, so 0 of 8 is not proof; the cause is
  removed for the measured case, and the pack that remains is for a model the worker has not seen).
- **The click and landing moments now run together.** The bench splits its window at the midpoint between the click
  and the cut row, and with the row 60 ms after the click that midpoint is 30 ms in, so in 2 of 8 runs (168 and
  150 ms) the 150 ms landing gap fell on the "click" side. It is the same rasteriser-bound landing as before
  (`bench/results/2026-11-22-render-009.md`), not a pack or a GC: the long task is 117-123 ms in every run.
- **The landing is unchanged** (149 against 152 ms headless), as `render-009` found it must be.

## The two observations from `core-085` that were not profiled

Profiled with a Playwright script on the same two-model scene (a zero-delay timer watching for gaps over 30 ms).

- **File menu open and close with two dense models, 279 ms headless:** Chromium, three open/close rounds, **no gap
  over 30 ms** in any of them, and the CPU profile of the rounds shows nothing app-side. WebKit: also no gap over 30 ms
  in 3 rounds. Not reproduced; it was most likely the redraw of the moment (the `render-009` cost), not the menu.
  No finding filed.
- **WebKit timer gaps 4-16 s into the worker's wait:** WebKit, three runs of the worker's measure wait (2.0-2.4 s with
  two models placed): **no gap over 30 ms 4-16 s in**, and none after the first second. Each run had one 56-64 ms gap
  at 76, 99 and 955 ms in, which is the moment the two placed models are drawn and measured, not an idle gap, and
  Chromium has none. With the cache the cut's wait is 60 ms, so the window the finding described no longer exists for
  a measured pair. No finding filed.
