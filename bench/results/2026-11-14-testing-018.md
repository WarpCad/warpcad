# `TODO/testing-018` (`ui-092` check 1): hover-to-painted in the Prompts view, on a copy of the owner's fan-duct project

- **Machine**: Apple M4 Pro, macOS 27.2.1, Node v24.22.2.
- **Browser**: Playwright 1.63.0, Chromium, **headless, software rasteriser**. GPU cost is not represented. Every conclusion below is about main-thread work and the frame cadence, not fill rate on a real GPU.
- **Build**: the **production build** (`npm run build`, served by `vite preview` on port 4173), per `.claude/prompts/perf-benchmark.md` rule 2. Built 2026-11-14 from the working tree on top of `4e52962`.
- **Fixture**: a **copy** of `~/Documents/fan-duct.ndjson` (571,332 B, 497 records, a `version: 2` state line with two prompts), loaded through **File ▾ → Open…**. It resolves to 3 bodies; each of the two requests lists all 3 as its parts. The file is the owner's own and is never committed, so this run is reproducible only against the same file. Viewport 1440 × 1300, so every request row and part row is on screen, clear of the offline toast.
- **Method**: `node bench/prompts-hover.mjs --file <copy> --runs 5 --rates 1,4 --cycles 15`. For each of five hover targets a real mouse (`page.mouse.move`) enters and leaves the target 15 times per run, 5 runs, 3 warm-up cycles discarded per target, a fresh browser context per run. CPU throttling (CDP `Emulation.setCPUThrottlingRate`) stands in for a phone: 1x and 4x. Each enter is timed from the delivery of the `pointerover` event (`performance.now()` in a capture listener) to (a) the first animation frame in which `data-frames-rendered` advanced, which is the frame that drew the change, and (b) the next animation frame after it, the next vsync, by which the drawn frame has been presented. That second number is the one called *hover-to-painted* here. Frame deltas are every `requestAnimationFrame` delta while the pointer works the targets, against a **control** that makes the same number of pointer moves over the Library column, where nothing hovers.
- **Why delivery time, not `event.timeStamp`**: a first version used the event's own stamp and read about 18 ms higher at p50. Chromium delivers input aligned to a frame, so the stamp predates delivery by up to a frame, which is the browser's cost and not the app's.
- **Hover targets**: the two collapsed request rows (each lights all 3 parts, 3 x-ray twins, which is the **twins-heavy case**: every lit body is drawn with a twin), and the three part rows of the first request when expanded (each lights 1 part, 1 twin). No hover produced a transient (hidden-part) mesh in this file.

## Reading it

- **At 1x, a hover is drawn about 2 ms after the pointer event arrives and presented at the next vsync, 15.0 to 15.2 ms at p50 on every target: inside one 16.7 ms frame.** The p95 is 15.6 to 16.2 ms. The twins-heavy rows (3 twins) cost the same as the single-part rows (1 twin) within the spread (p50 15.1 to 15.2 against 15.0 to 15.1). Leaving a row clears the highlight at the same speed (p95 16.0 to 16.2).
- **The tail is whole dropped frames, not slow ones.** The worst enter at 1x is 32.6 ms, exactly two frames. Two of the 375 enters (5 targets x 75) did that at 1x, and 5 of 9,303 frames passed 25 ms against 0 of 1,861 in the control.
- **At 4x CPU the median still lands in one frame (15.2 to 15.4 ms) but at least 5% of enters take two** (p95 31.0 to 31.8 on four of five targets), and 49 of 9,301 frames passed 25 ms (0.5%) against 0 in the control. The hover does cost something at 4x; the cost is a dropped frame now and then, not a stall. Nothing came near the 90 ms shader recompile `TODO/ui-049` found and fixed.
- **Verdict against the target of one 16 ms frame**: met at p50 and p95 on the laptop-class run, with an occasional second frame in the tail, more often at 4x. No finding filed: the budget in `CLAUDE.md` is a 16 ms frame during pan, zoom and drag, and the hover meets it at the median under both rates. A real GPU is not represented, so a device with a slower rasteriser than this software one remains a hand check (`ui-092` #3). Part rows carry the same numbers as the request rows, so the twin count is not what costs the second frame.
- Not run: heap across repeated sweeps (`bench/hover-sweep.mjs` covers the leak check for the Objects-list hover, which shares the highlight code) and a CPU profile of the 2-frame tail (it is not over budget).
