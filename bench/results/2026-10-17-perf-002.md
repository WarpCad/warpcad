## 0. Method in one paragraph

**Usable** is measured inside the page from navigation start: the viewport has drawn its first
frame (`[data-testid=viewport]` with `data-webgl="ready"` and `data-frames-rendered` ≥ 1) **and**
the Library's Cube row (`library-row-primitive.cuboid`) is laid out and enabled; that moment is
**ready**, and **usable** is the second animation-frame callback after it (a frame carrying that
DOM was produced and the main thread was free). **Cold** is a fresh browser context's first load;
**repeat** is a second navigation in the same context once the service worker has installed,
activated and taken control (every repeat in every cell was served by the worker). Bytes and
requests are counted **at the server**; the worker's own traffic (its script, Workbox, the
precache, recognised by `Referer: …/sw.js`) is reported separately as **SW install**.
Throttling, applied in the server so it is identical in all three engines: **`none`** (localhost);
**`slow4g`**: 150 ms before each request is handled plus one shared 1.6 Mbit/s (200 kB/s) link for
every byte sent, Lighthouse's mobile network numbers; **`slow4g-cpu4`**: `slow4g` plus a 4× CPU
slowdown, **Chromium only** (Firefox and WebKit have no CPU throttling in Playwright). TCP/TLS
handshakes are not modelled.

## 1. What the build ships today (fresh values, not the request's)

`vite build` at `cae5acf`: the entry chunk `index-*.js` is **1,825.20 kB (549.46 kB gzip)**, above
the 500 kB warning. The request quoted 1,812.57 / 541.04 kB; the difference is the last few days'
commits. It is not alone at startup: `index.html` also `modulepreload`s the shared
`watertight-*.js` (176.64 kB / 54.60 kB gzip). Measured at the server on a cold load, every
engine fetches exactly **5–7 requests before usable**: `index.html`, the CSS (168 kB / 24.1 kB
gzip), the two chunks above and `workbox-window` (5.65 kB), plus the manifest/icon in Firefox and
WebKit: **601.4 kB of JavaScript on the wire, 2,007.5 kB uncompressed**. The four workers
(evaluation 412.6 kB, export 524.8 kB, mesh, image) are **not** fetched before usable.

The service worker then precaches **188 entries, 21.8 MB**: measured on the wire, **189 requests,
19.6 MB** after every cold load, almost all of it Help text and still images
(`scripts/vite-plugin-help.mjs`'s `HELP_PRECACHE_GLOBS`). That is ~33× the app's own JavaScript.
It happens after usable and does not delay it (section 5), but on a metered phone connection it is
the dominant cost of a first visit, and no chunking change touches it.

Notes on the candidates:

- **`codeSplitting` is the API this Vite/Rolldown accepts** (Rolldown 1.2.12; `manualChunks` and
  `advancedChunks` are deprecated and ignored when it is set). A first `three` group matching all of
  `node_modules/three/` pulled the lazily imported `GLTFExporter` (36.7 kB) into the initial `three`
  chunk; matching `three/build/` only keeps it lazy. vendor-split moves no bytes, it only cuts them
  into 7 files: its app chunk is still 1,091.5 kB, so **it does not even clear the warning**.
- **defer-sentry** is the one change that is both small and safe in isolation: −115.5 kB raw /
  −38.9 kB gzip. With a DSN set (as the Pages build has, if the repository variable is set) the
  SDK would be fetched after boot, and an error thrown before it lands would not be reported.
- **defer-surfaces**: lazy components alone moved little, because the AI tool registry stayed
  reachable from boot through three static edges (`useAgent` → `ai/agent.js`, `useWebMcp` →
  `webmcp/register.js`, and `stores/assistant.js` → `ai/providers/scripted.js`, a dev-only
  provider shipped in production). With all three made lazy, AI code at boot fell from 139 kB to
  30 kB. Rolldown's automatic splitting then cut the shared remainder into **21 modulepreloaded
  chunks**. The seven sheets are mounted unconditionally by AppView (each hides itself), so their
  chunks are still fetched right after mount, before usable, as the request counts show; only
  the agent, the tool registry and Sentry are truly deferred to first use.
- **surfaces-1chunk** puts everything reachable at boot back into one chunk (`$initial` tag);
  lazy surfaces stay split.

## 4. Each candidate is still a whole app

`node bench/bundle-load.mjs --check …`, all five builds × three engines, unthrottled: cold load to
usable with **no console error and no page error**; the Assistant opens (with no key stored, its
key sheet, itself deferred in the split builds); Help opens and closes; the service worker takes
control; **every JavaScript file the build emitted is in the worker's Cache Storage** (lazy chunks
and the four workers included); then, with the **server offline** (every socket destroyed), a
reload reaches usable again from the worker and the Assistant still opens.

**15/15 pass, all 7 steps.** Offline is genuinely exercised in WebKit too: Playwright's
`context.setOffline` takes the network away beneath WebKit's service worker and fails even the
unchanged baseline (as `e2e/pwa-update.e2e.js` records), but taking the *server* offline leaves
the worker in charge, and every build reloads from its precache.

vite-plugin-pwa's `globPatterns: ['**/*.{js,…}']` already precaches every split chunk: precache
entries grow with the chunk count (188 → 189 / 193 / 212 / 232) at a cost of under 0.1 MB.

usable (median), counted at the server; the worker's precache is not in them. Zero console or page
errors and zero failed loads in all 490 recorded loads of the five-build batch (245 cold, 245
repeat), and every repeat load was served by the service worker (`repeat-sw` in every cell). Raw per-load samples:
`bench/bundle-load.mjs --json` (not committed; reproduce with the commands at the top).

Δ against baseline, median: defer-sentry **−197 / −200 / −196 ms** (−5 %); surfaces-1chunk **−384 /
−418 / −407 ms** (−10 to −11 %); defer-surfaces −350 / −647 / +40 ms. The spreads are ±10–20 ms,
so every difference above ~50 ms is repeatable.

This state is **transfer-bound**: 627 kB on a 200 kB/s link is 3.1 s of the 3.7 s, and the savings
track the bytes at almost exactly the link rate (defer-sentry: 38.5 kB → 197 ms; at 200 kB/s that
is 193 ms). Two engine effects sit on top of the bytes:

- **Firefox gains from more files even with no fewer bytes**: vendor-split saves 264 ms there
  (none in Chromium or WebKit), and defer-surfaces' 21 chunks beat surfaces-1chunk's one by 229 ms.
  Firefox appears to compile each script off the main thread as it arrives, so several scripts
  overlap compiling with downloading. Chromium already streams one script.
- **WebKit's defer-surfaces is bimodal**: 5 of 7 runs at ~3,810 ms with 43 requests before usable,
  2 of 7 at ~3,390 ms with 31. The sheets AppView mounts at startup fetch their own chunks over
  HTTP/1.1 at 150 ms each, and when those fetches land before usable they compete with the boot
  chunks for the link. surfaces-1chunk, with 12 requests, never does.

### 5d. Where the remaining unthrottled time goes (Chromium)

In Chromium, usable trails DOM-ready by ~115 ms in every build, cold and warm (Firefox and WebKit:
~40 ms), and first-contentful-paint lands with usable, not with ready. A CPU profile of 5 warm
loads of the source-mapped baseline (scratch probe, not committed) puts **~10 ms** of that in
JavaScript and **~126 ms in `(program)`**: native work outside JS (style, layout, paint and the
GPU process's shader compile and link under SwiftShader; `getProgramInfoLog` is among the top
callers). That is a headless software-GL cost, the same in every build, and not something the
bundle can change. It was not pursued further, and it says nothing about a real GPU.

## 6. Tradeoffs

- **Extra requests.** vendor-split: 10–11 page requests before usable instead of 5–7; defer-surfaces
  30–44; surfaces-1chunk 12–24. Under 150 ms of latency per request (HTTP/1.1, 6 connections) that
  fragmentation is what made defer-surfaces bimodal in WebKit. GitHub Pages serves HTTP/2, which
  would soften this, but that was not measured.
- **Delayed feature load.** Every deferral moves bytes to first use. The Assistant's agent and tool
  registry (~26 kB gzip) load on the first send/attach, and Sentry, when a DSN is set, after boot:
  **an error thrown during boot, before the SDK lands, would not be reported** unless it is
  buffered (perf-003). The async sheets are fetched right after mount because AppView mounts them
  unconditionally, so they defer almost nothing and cost a repeat-visit frame at 4× CPU.
- **PWA / offline.** Nothing breaks: the precache glob already takes every chunk (section 4), and a
  split adds 1–44 precache entries for under 0.1 MB. The 19.6 MB precache itself, almost all Help
  stills, is ~33× the app's JavaScript and dwarfs any chunking saving on a metered first visit.
- **Deploy delta** (what a returning user's worker re-downloads in the background after a deploy
  that changes one line of app code; measured by rebuilding each candidate with a one-line
  `LibraryPanel.vue` change and diffing the hashed file names): the one-chunk shape (measured on
  defer-sentry) re-fetches 4 files, 1,751 kB raw / 519.5 kB gzip; **vendor-split re-fetches 3
  files, 1,096 kB / 344.8 kB**, about 175 kB gzip less per deploy, because the vendor chunks keep
  their hashes; surfaces-1chunk re-fetches 18 files, 1,934 kB / 584 kB, because every lazy chunk
  imports the rehashed entry and is rehashed with it. This is bandwidth in the background
  (`registerType: 'autoUpdate'`, the toast offers Reload), not load time.
- **The warning stays.** No candidate except defer-surfaces (511 kB, fragmented) brings the
  largest chunk under 500 kB. A boot graph of three.js, Vue, `@jscad/modeling` and the document
  core is ~1.6 MB minified by itself.

## 7. A sixth build: defer only what is unused at boot (**defer-boot**)

Sections 5 and 6 separate two different things. *Splitting* the boot graph (vendor-split, the
21 chunks) moves no bytes and helps only Firefox. *Lazy sheets* defer almost nothing and cost a
repeat-visit frame. **Deferring code that is not used at boot** (Sentry without a DSN, the agent,
the WebMCP tool registry, a dev-only provider) moves the bytes. None of the first five builds was
exactly that, so it was built and measured on its own: **surfaces-1chunk with `AppView.vue`
restored**, i.e. four source files changed (`core/errorReporting.js`, `composables/useAgent.js`,
`composables/useWebMcp.js`, `stores/assistant.js`) plus the one `codeSplitting` group

## 8. Verdict

**The chunk-size warning does not, by itself, justify a split.** The initial chunk is dominated by
code the first frame needs: three.js, `src/core` (the main-thread fold and the Library's recipes),
the components on screen, Vue and `@jscad/modeling`, ~70 % of it. Cutting that into vendor chunks
(the warning's own suggestion) changes nothing in Chromium or WebKit, costs extra requests, and
still leaves a 1,091 kB chunk over the limit. On a fast connection every build is usable in
120–240 ms in every engine, and on a repeat visit, which the service worker serves with no network
at all, chunking cannot matter. `chunkSizeWarningLimit` should stay as it is: raising it would
hide the number without changing a byte.

**What is warranted is smaller and different: stop shipping code that is unused at boot.** Measured
in all three engines, with the production build, cold, on a slow link, deferring Sentry (inert
without a DSN), the AI agent and its tool registry (loaded on first send), the WebMCP registry
(loaded only where `navigator.modelContext` exists) and a **dev-only** scripted provider that ships
in production today makes the first visit **~330 ms (≈9 %) faster in Chromium, Firefox and WebKit
alike**, with no cost on repeat or fast loads. That is user-visible on a first visit over a mobile
link, and the change is four source files and one config line. It is filed as
**`TODO/FIND-perf-003-defer-code-unused-at-boot.md`** with the measured targets.

Not recommended: lazy `defineAsyncComponent` sheets while AppView mounts them unconditionally
(they load at mount anyway, fragment the build, cost 10–13 ms per repeat visit at 4× CPU and made
WebKit bimodal); vendor chunks for load time (Firefox only, +5 requests). Vendor chunks *would*
cut what a returning user re-downloads after each deploy by ~175 kB gzip (section 6). That is a
bandwidth question for a later task, not a load-time one.

## 9. What was not measured, and why

- **A real phone, a real GPU, a real network.** Headless engines with software GL; throttling is
  emulated in the server (latency + bandwidth, no TCP/TLS handshakes, no packet loss), and CPU
  throttling exists only in Chromium. The absolute numbers are this laptop's; the deltas between
  builds are the result. `TODO/VERIFY.md` carries the real-device checks.
- **HTTP/2.** `vite preview` serves HTTP/1.1. GitHub Pages serves HTTP/2, which would soften the
  per-request cost that hurt the fragmented builds; the one-chunk builds are unaffected by it.
- **A build with a Sentry DSN or GA ID.** The DSN would make the page post to sentry.io, and GA to
  Google, from the bench; neither was configured. So `Sentry.init`'s own boot cost and the deferred
  SDK's later fetch are unmeasured; only the SDK's download/parse cost is.
- **An AI turn after the deferral** (the agent and tool-registry chunks' first import), and the
  dev-only scripted path (`npm run dev` only); see section 7.
- **Phone and tablet viewports.** This task changes no layout; laptop 1440×900 only, as specified.
- **Time-to-interactive beyond the first painted frame** (long tasks after usable): not measured;
  usable already requires the main thread to run a second animation-frame callback.
- **The Help precache's cost** (19.6 MB on a first visit) is reported but not optimised; it is not
  a chunking question.
