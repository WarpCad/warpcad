# data-011 — merge section overhead (2026-10-12)

`node bench/merge-section-overhead.mjs`, documents built through the command layer with a
random replica id, saved with `serializeProject`.

| Document | File | Records | `merge` section | Share of file |
|---|---|---|---|---|
| Scenario 3 — snap-placement (Pi, cube, one snap) | 826 B | 4 | 278 B | 33.7% |
| Scenario 12 — 8 placements and a mid-history edit | 1 560 B | 8 | 647 B | 41.5% |
| Scenario 17 — 12 ribs, one removed, one undone | 2 024 B | 10 | 877 B | 43.3% |
| 200 placements | 38 793 B | 200 | 16 237 B | 41.9% |

**Over the one-third line the task set**, on every document that is edited in place. These
records are small (about 110 B each); a project with sketches or user parts is dominated by
its records and sits well under it. Where the bytes go, per row: the position key (about 22
characters, plus the row id spelled again as its map key) and the `born` stamp (a counter and
a six-character replica id, spelled out every time).

## Proposed tighter encoding (not built — needs its own task and a version-2 reader change)

1. **Derive the common position key.** A row appended after its predecessor by the replica
   that wrote it has key `keyBetween(previousKey, null, born)`; the writer can omit `pos`
   whenever that holds and the reader recompute it in file order. For an append-only history
   this removes `pos` entirely (about 45% of the section).
2. **Replica table.** Write each replica id once (`"r":["hhhhhh","oooooo"]`) and stamps as
   `[counter, index]`, which cuts about 6 bytes per stamp.
3. **Rows by position, not id.** `stamps` as an array parallel to the record lines instead of a
   map keyed by row id, so ids are not repeated (about 12-25 B per row).

Together these should bring the append-only cases to roughly 10-15% of the file. They are
reader-visible changes to a format that has now shipped, so they want a decision, not a
quiet edit.
