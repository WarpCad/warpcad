# `TODO/render-009`: does an indexed result mesh speed up the landing of a dense whole-model cut?

**Machine**: Apple M4 Pro, macOS 27.2.1, Node v24. **Browser**: Chromium, 1440x900, production build.
**File**: two copies of the owner's `5036 RGB Matrix 2.5mm/5036 RGB Matrix.3mf` (1.9 MB, 25 parts, 219,540
triangles each; never committed), whole-model Subtract, as `bench/results/2026-11-19-core-085.md`.

**Answer: no.** The finding proposed welding the result onto shared vertices (about 110 k for 220 k triangles,
against 660 k) and drawing it with a flat-shaded material. It was built (a typed-array open-addressing weld in
`geom3ToBufferGeometry`, no normal attribute, `flatShading: true` on the body material) and measured, and then
**reverted**: it did not change the landing, headless or on the GPU. The rasteriser is the floor.

## The bench, before and after the change

```
npm run build && npx vite preview --port 4173 &
node bench/evaluation-mainthread.mjs --only whole-model-cut --mesh "<file>" --rates 1 --runs 3            # headless
node bench/evaluation-mainthread.mjs --only whole-model-cut --mesh "<file>" --rates 1 --runs 3 --headed   # the Mac's GPU
```

| Moment | Before, headless | Indexed, headless | Before, GPU (`--headed`, 2026-11-19) | Indexed, GPU |
|---|---|---|---|---|
| Longest timer gap at the click | median 22 ms (worst 23) | median 22 ms (worst 23) | median 14 ms | median 21 ms (worst 22) |
| Longest timer gap at the landing | median 141 ms (worst 168) | median 144 ms (worst 145) | median 47 ms (worst 48) | median 47 ms (worst 49) |
| Long Task at the landing | median 119 ms | median 117 ms | none | none |

(The GPU click gap of 21 ms against 14 ms on 2026-11-19 is the headed idle floor of this session, 18 ms a frame here
against 9-10 ms then; it is not the change, which touches nothing at the click.)

The weld itself costs what the normals it replaced cost: a Node microbench of a 217,800-triangle grid took 9-19 ms
for the welded build and 9-16 ms for the non-indexed build with `computeVertexNormals`. So the app side neither
gained nor lost.

## Why: the rasteriser is triangle-bound, not vertex-bound

`node bench/raster-triangle-cost.mjs` draws a displaced grid in a bare three.js scene, non-indexed against indexed
with flat shading, at three triangle counts, and times `render` plus a one-pixel `readPixels` (median of 5 warm
frames, 1440x900):

| Triangles | Non-indexed (vertices, headless) | Indexed + flat (vertices, headless) | Non-indexed, GPU | Indexed, GPU |
|---|---|---|---|---|
| 54,450 | 163,350 v, 22 ms | 27,556 v, 22 ms | 1 ms | 1 ms |
| 108,578 | 325,734 v, 39 ms | 54,756 v, 38 ms | 2 ms | 1 ms |
| 217,800 | 653,400 v, 74 ms | 109,561 v, 72 ms | 1 ms | 1 ms |

A six-fold cut in vertices moves the frame by 2 ms; doubling the triangles doubles the frame. SwiftShader's cost is
per triangle (setup and binning), so no vertex sharing can reach the 50 ms target while the result has 220 k
triangles: 74 ms for the result alone is already over it. The only lever on that would be drawing fewer triangles
(a level-of-detail or decimated stand-in while the camera is moving), which changes what the user sees and is not
worth doing for a rasteriser real users do not have: on a GPU the same frame is 1-2 ms and the landing already
passes (median 47 ms, no Long Task).
